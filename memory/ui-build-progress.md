**Ambient video background — significant back-and-forth, now stable:**
- User supplied a real 1-hour green gradient/ribbon MP4 at the project root (`Green Gradient Background Wallpaper 1 Hour...mp4`, 588MB). Trimmed via ffmpeg to a ~30s clip, slowed to ~0.33x speed (`setpts=3.0303*PTS` — note: raw-source duration must be captured with `-ss`/`-t` **before** `-i`, applying `-t` after `-vf setpts` only truncates the *output*, doesn't get you a full slowed clip — hit this bug once), then a self-referencing `xfade` crossfades the clip's own tail into its own head for a seamless loop. Final asset: `src/UI/Assets/ambient_loop.mp4` (~2.4MB), copied to output via `<None CopyToOutputDirectory>` in `UI.csproj`.
- First attempt at "living background" was a **procedural animated gradient** (no video) — rejected by user as not filling the screen properly / not what they wanted; abandoned in favor of the real video once the user supplied footage.
- **Loop stutter fix:** a single `MediaElement` restarting via `Position=0; Play()` on `MediaEnded` causes a visible decoder re-seek hitch even with a seamless video file. Fixed with **two overlapping `MediaElement`s** (`PlayerA`/`PlayerB`) both playing continuously, permanently offset by half the clip duration, crossfading opacity ~0.5s before whichever is active reaches its end, then swapping roles. Whichever player is currently invisible is the one that silently restarts via `MediaEnded`, so the restart hitch never appears on screen. This is the ambient background's final architecture — don't regress to single-player + hard restart.
- **Load-order fix:** `MediaOpened` (real first-frame-decoded event) gates a `MediaReady` event on `AmbientBackground`, which `MainWindow` uses to keep `ContentGrid` at `Opacity="0"` until the video is genuinely ready, then fades in over 0.35s — otherwise tiles/rail flash in over a black background before the video decoder starts.
- **Frosted glass:** `BlurEffect Radius="28"` on both `MediaElement`s (WPF has no native Acrylic/Mica backdrop blur) plus a light `#14FFFFFF` wash on top of the existing dark scrim.
- Theme default is `MeadowGreen` (matched to the video's actual sampled palette — yellow-green ribbon highlight, deep green field) — must apply the theme **before** `base.OnStartup(e)` in `App.xaml.cs`'s `OnStartup` override, since `StartupUri` constructs `MainWindow` (and its view model, which generates theme-tinted tile art) as part of that base call — got this backwards once and tiles rendered with the wrong/default theme.

**Hard-won WPF rendering lessons (don't repeat these mistakes):**
1. **`Border.CornerRadius` does not clip child content.** A rounded outer `Border` containing separately-shaped inner content (e.g. a flat-cornered art panel `Border`) will show that inner content's real corners poking through/mismatched, especially once anything scales. Fix used: either (a) give inner content a matching partial `CornerRadius` so there's no seam in the first place (used for the hero-adjacent bottom scrim), or (b) make the outer element's own `Background` directly hold the art brush so there's only ONE shape, no inner rectangle at all (used for library tiles — the art brush paints the card `Border`'s own `Background`).
2. **`Clip` (a `RectangleGeometry`) combined with a `RenderTransform` that scales the element produces a visible tearing/seam artifact in WPF** — confirmed empirically by disabling the scale animation and watching the artifact disappear entirely. Do NOT combine per-element `Clip` geometry with a scaling `RenderTransform` on the same element. The hero panel is safe to use `Clip` (via `SizeChanged` → `RectangleGeometry`, since `Rect` isn't a `DependencyObject` so its Width/Height can't be data-bound in XAML) because it only fades/translates, never scales.
3. **A `Style.Setter` for a reference-type property (`RenderTransform`, `Effect`) shared across multiple `DataTemplate`-generated instances can cause `Storyboard.TargetProperty` paths like `RenderTransform.ScaleX` or `Effect.Opacity` to throw `XamlParseException: Cannot resolve all property references`.** Fix: give each templated instance its OWN `RenderTransform`/`Effect` object declared directly in the `DataTemplate`, not via a shared `Style.Setter.Value`. (Ended up simplifying further by not animating `Effect.Opacity` at all — snap the DropShadowEffect opacity via a plain `Setter`, only animate `RenderTransform.Scale{X,Y}`.)
4. **Scaling a focused list item beyond its own resting layout box gets clipped by ancestor containers (`ScrollViewer`'s internal `ScrollContentPresenter`, `ItemsControl`, row `Grid`s) no matter how much margin/padding headroom is added** — `ScrollViewer` clips to its viewport internally regardless of `ClipToBounds` settings on it or ancestors. Spent many iterations trying to defeat this via negative-margin/padding tricks on every ancestor; none reliably worked. **The actual fix that worked: invert the animation direction.** Every tile's resting/default `ScaleTransform` is set to `0.94` (not `1.0`), and gaining focus animates UP to `1.0` (full size) while losing focus animates back down to `0.94`. This means NO tile ever renders larger than its originally-allocated layout box — there is nothing to clip, since "focused" is just "full-size," not "oversized." Apply this same technique to any future WPF focus-scale-on-item-in-a-list effect — do not repeat the grow-past-bounds approach.
5. Screenshot verification of this WPF app via PowerShell `CopyFromScreen` was unreliable in this dev environment (captured stale/wrong-window frames, `SetForegroundWindow` timing issues, sandboxed remote-display quirks) — burned significant time chasing a phantom bug from a misleading crop before the user's own screenshot corrected the diagnosis. When debugging visual issues here, prioritize asking the user for a screenshot/description over trusting automated screen capture in this sandbox.
6. **Setting `Visibility = Visible` on a previously-`Collapsed` element does NOT trigger a synchronous layout pass.** Reading `ActualWidth`/`ActualHeight` immediately afterward (same method call) still returns 0/stale values, since WPF's layout system runs on the next layout/render cycle, not inline. Any animation built `From`/`To` using those values at that point animates toward 0 instead of the real size. Fix: defer the read (and the animation setup that depends on it) via `Dispatcher.BeginInvoke(..., DispatcherPriority.Loaded)` so a layout pass happens first. Hit this exact bug building the launch-overlay "swallow" grow animation — the tile visually shrank/slid instead of expanding to fill the screen, until the read was deferred.

**Multi-section dashboard + focus-follows-navigation model (major rework):** dashboard expanded from one "LIBRARY" row to four sections — RECENTLY PLAYED, DOWNLOADS, LIBRARY, STORE. Required a real navigation-model rewrite, not a patch:
- `DashboardRowViewModel` (new) — one per navigable row (Recently Played/Downloads/Library), each owning its OWN `GameTileViewModel` instances. **Critical lesson:** the first attempt reused the SAME `GameTileViewModel` objects across rows (e.g. a game appearing in both "Recently Played" and "Library" was literally one shared object) — this breaks focus entirely once cross-row navigation exists, since `IsFocused` lives on the shared instance and would light up in two rows at once. Always give each row its own tile instances built via separate `GameTileViewModel.FromEntry()` calls, even for the same underlying `GameEntry`.
- `MainWindowViewModel.Rows` holds the navigable rows in top-to-bottom order; `StoreItems` (a separate, non-`GameEntry`-backed `StoreItemViewModel` list — Store shows not-yet-installed placeholder games, which isn't a concept `ConsoleLibrary.GameEntry`'s schema models) is bound separately and is NOT keyboard-navigable in this build.
- **Up/Down moves focus BETWEEN rows** (`MoveBetweenRows`, skips non-navigable/empty rows, no wraparound at top/bottom), **Left/Right moves WITHIN the current row** (`MoveWithinRow`) — this is the correct console-navigation split; earlier attempts conflated "scroll the page" with "move focus" as two separate, disconnected actions, which was explicitly rejected by the user ("the highlight must follow the keyboard... focus of the little aura thingy must follow").
- Default focus starts on the FIRST row (index 0, typically Recently Played), not Library — matches how a real console home screen starts top-left. Got this wrong once (started on Library, which is usually the LAST row, so pressing Down appeared to do nothing / lose the highlight since there was nowhere below to go).
- The camera (scroll position) FOLLOWS focus via a `FocusedTileChanged` event → `MainWindow.xaml.cs` computes the newly-focused tile's real on-screen position (visual-tree search by DataContext reference, `FindByDataContext`, since tiles now live under nested per-row `ItemsControl`s rather than one named control) and smoothly animates `ScrollViewer.VerticalOffset` via a manual `DispatcherTimer` easing loop (`ScrollViewer.VerticalOffset` has no dependency property, so `BeginAnimation` can't target it directly — this stepped-timer approach is the workaround). Do NOT reintroduce a separate "Up/Down scrolls the page directly" key handler — that was tried first and explicitly rejected by the user as disconnected from the actual focus/highlight.
- **Real bug hit and fixed:** nesting 4 horizontal `ScrollViewer`s (one per row) inside one outer vertical `ScrollViewer` caused the whole layout to collapse to near-zero height — only the first section's label was visible, everything else invisible. Fixed by removing all per-row `ScrollViewer`s entirely; at the fixed 1280px test-window width, 3-4 tiles per row fit without needing horizontal scroll, so a plain `ItemsControl`/`StackPanel` per row has no such ambiguity.
- `GameTileTemplate`/`StoreTileTemplate` were extracted as shared `Window.Resources` `DataTemplate`s (previously the tile markup was duplicated inline per row) — **ordering matters**: a `DataTemplate` referencing `{StaticResource LibraryCardStyle}` must be declared AFTER `LibraryCardStyle` in the resource dictionary, or it throws `XamlParseException: Cannot find resource named 'LibraryCardStyle'` at runtime (WPF resolves `StaticResource` in document order within the same dictionary).
- `GameIconLoader.cs` — resolves `GameEntry.ImageUrl` (treated as a filename relative to `Assets/Icons/`) into an `ImageSource`, returns null gracefully if the file doesn't exist yet (no real icon files exist in this build — user asked to hold off verifying until real images are supplied). Wired into tile templates via `NullToVisibilityConverter` so the icon slot collapses cleanly when absent instead of showing a broken image.
